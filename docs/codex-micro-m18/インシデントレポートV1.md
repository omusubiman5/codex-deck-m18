# Codex Deck M18 インシデントレポート V1

> **訂正（2026-08-20 / V5）**：本書の`APPR`、`DEL`、`PLAY`を「危険キー3種」とした分類には公式根拠がなく、誤りだった。V5で分類、長押し処理、警告表示を撤去した。公式30キーはすべて通常の単押しで使用する。Rate-limit Resetだけは別機能として長押し確認を維持する。

## 1. 文書情報

- 発行日：2026-08-20
- 対象：Windows版Codex Desktop、Codex Deck watcher、VSD Craft連携
- 重大度：P0／リリース停止
- 状態：未解決。是正実装とlive再試験待ち
- 関連文書：`実装計画書V2.md`、`テスト計画書V1.md`、`テスト結果V1.md`

## 2. 要約

Codex Deckの自動回復処理が、bridge未接続を検出した際に、稼働中のCodex Desktop全体へ`-ForceRestart`を要求できる状態だった。実ログでは、2026-08-20 01:13:52に自動回復が開始され、01:14:09にCodex配下の9 processを終了したことを確認した。

この処理は対象のCodex Deck bridgeだけを回復するものではなく、他の稼働中タスクやセクションを含むCodex process群を一括終了する。したがって、「他のセクションが動いている状態でCodexを再起動しない」という安全要件を満たしていない。

watcher単位の1回制限、30分cooldown、main process数の確認は、発生頻度を抑える対策ではあるが、稼働中Codexを自動終了できる権限自体を残しているため恒久対策ではない。

## 3. 影響

### 確認済み

- Codex Deck watcherから強制再起動経路が実行された。
- launcherがCodex配下の9 processを終了した。
- Codex Desktopの他タスク／セクションも同じprocess群に含まれるため、局所的なbridge回復に限定できなかった。
- 単純起動、VSD Craft追加起動、45操作matrixのlive合格証跡がない状態で、実機合格と判断していた記録があった。この合格判定は撤回済みである。

### 未確認

- 未送信入力やタスク状態の恒久的なデータ消失は確認していない。
- macOSで同一経路が発生した証拠は今回の調査では確認していない。
- クラッシュの全件が本経路だけを原因とするとは確定していない。

未確認事項を合格または無影響とは扱わない。

## 4. 証跡

`%LOCALAPPDATA%\CodexDeck\watcher.log`に次の記録がある。

```text
[2026-08-20T01:13:52.2394927+09:00] Codex 26.814.5167.0 started without the bridge; performing the single permitted automatic recovery restart.
[2026-08-20T01:14:09.7924414+09:00] Launcher: Closing 9 Codex process(es)...
[2026-08-20T01:14:12.4723140+09:00] Healthy Codex Deck bridge detected for Codex 26.814.5167.0 on port 54808.
[2026-08-20T01:18:38.9813032+09:00] Codex generation 26.814.5167.0:7208 is running without the bridge and was left untouched (watcher recovery budget exhausted).
```

関連する実装経路は次のとおりである。

1. `launcher/Start-CodexDeck.ps1`がstartup shortcutへ`-RecoverExistingSession`を設定する。
2. `launcher/Watch-CodexDeck.ps1`が回復条件成立時にlauncherを`-ForceRestart`付きで呼ぶ。
3. `launcher/Start-CodexDeck.ps1`がCodex配下のprocessを列挙し、`Stop-Process -Force`で終了する。

さらに、`Start-CodexDeck.ps1`は`-ForceRestart`がない場合でも、bridge portがなくCodex processが存在すると終了経路へ入る。明示的な再起動同意と通常起動が分離されていない。

## 6. 根本原因

### 6.1 直接原因

bridge回復とCodex Desktop再起動を同じ操作として実装し、自動watcherへ強制再起動権限を与えたこと。

### 6.2 設計原因

- bridgeがない状態を「Codex全体を再起動してよい状態」と誤って扱った。
- Codex process群の共有範囲を考慮せず、他タスク／セクションを保護する境界がなかった。
- 通常起動、観測、手動再起動の権限がlauncher内で明確に分離されていなかった。
- 回復回数の制限を安全要件として扱い、破壊的操作の自動実行禁止を完了条件にしなかった。

### 6.3 試験原因

- 初期テスト計画が45操作の配置と配送を先行し、単純起動をGate 1に置いていなかった。
- ソース文字列、UUID、handlerの存在確認を、アプリ起動安定性やCodex側の操作成立と混同した。
- 実際にCodex Desktopを起動していない試験結果からlive合格を判断した。
- 自動回復の「最大1回」を検査したが、「自動強制再起動が0回」を要求していなかった。

## 7. 併発・潜在不具合

鬼レビューでは、今回の強制再起動とは別に次の不具合を確認した。いずれもV2是正対象とする。

1. シーン切替時、旧面の非同期画像描画が新面を上書きできる。
2. current-view依存commandの不成立をtransport障害と同じcatchで処理し、CDP接続を切断する。
3. `APPR`、`DEL`、`PLAY`を危険キーと文書化したが、実装は通常キーと同じ単押し即時実行である。
4. READMEの「動作確認済み」という表現が、live不合格のテスト結果と矛盾する。

## 8. 暫定措置

- 現状をマージ／リリース可能と判定しない。
- Codex DeckからCodex Desktopを自動再起動する試験を行わない。
- live試験は、対象Codex task自身ではなく、別terminalまたは外部観測者から実施する。
- Gate 1とGate 2に合格するまで、危険キーおよび45操作matrixを実行しない。
- 現行ログ、profile、plugin、launcherのバックアップを保持する。

## 9. 恒久対策と完了条件

恒久対策は`実装計画書V2.md`に従う。少なくとも次をすべて満たすまで本インシデントを解決済みにしない。

- 自動watcher、startup shortcut、通常launcherの全経路から、稼働中Codexを終了する処理が到達不能である。
- `Stop-Process`は明示的な手動再起動操作でのみ実行でき、実行前に対象と影響を表示する。
- current-view依存commandの不成立でCDP transportを切断しない。
- シーン切替後に旧描画が新面を上書きしない。
- 危険キー3種が通常キーと区別され、誤った短押しで実行されない。
- Codex単純起動5分、VSD Craft追加起動5分で、単一起動、クラッシュ0、意図しない再起動0を確認する。
- 最小smokeと45操作matrixを順序どおり完了し、証跡を`テスト結果V1.md`へ記録する。

## 10. 判定

本件は、発生頻度を制限する修正だけでは解決しない。自動処理からCodex終了権限を除去し、別主体によるlive安全試験と45操作の効果確認を完了した時点でのみクローズする。
