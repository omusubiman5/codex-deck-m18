# Codex Deck M18 実装報告書 V1

## 1. 実施概要

- 実施日：2026-08-19
- 実装ブランチ：`codex/feature/m18-v1`
- 対応計画：`実装計画書V1.md`
- 基準テスト：146件合格
- 実装後テスト：154件合格

M18の15 LCDキー×3シーンへ必須45操作を重複なく収容した。下段3ボタンは左・中央・右からシーン1・2・3へ直接切り替える。AgentキーはCodexのタスク名だけでなく、取得できたプロジェクト／workspace名を優先表示する。

併せて、固定配列へ操作を直書きしていたM18実装を、操作カタログ、レイアウト、binding生成、scene管理へ分割した。

## 2. 実装結果

### 2.1 45操作の単一定義

`src/action-catalog.ts`へ次を集約した。

- Agent 6件
- Joystick 4方向
- Reasoningエンコーダ押下
- Windows／Macホスト切替＋health
- Usage Limit／Overview／Reset
- 公式30キー
- 各物理操作から既存manifest UUIDへの対応

起動時検査と単体テストにより、45件、ID重複なし、公式30件との完全一致を保証する。manifestの既存53アクションは削除せず、保存済みVSD Craft配置との互換性を維持した。

### 2.2 15×3シーン

`src/m18-layout.ts`を唯一の盤面定義として追加した。

| シーン | 内容 | 個数 |
|---|---|---:|
| 1 | Agent 6、Joystick 4、Encoder 1、Host 1、Usage 3 | 15 |
| 2 | 公式キー`FAST`～`DIFF` | 15 |
| 3 | 公式キー`PLAY`～`APPS` | 15 |

全シーンを平坦化した結果が45件かつ一意であることを自動検査する。

### 2.3 下段3ボタンの面切替

`src/m18-scene-controller.ts`を追加し、下段キー15～17をシーン1～3の直接選択へ変更した。

- 現在面に依存しない直接遷移
- 旧面の表示登録を解除してから新面を登録
- 再起動時はシーン1
- 押下中に面を切り替えても、releaseは押下開始時のbindingへ配送

旧`environmentAction1`～`environmentAction3`の下段固定割当はM18直接接続ランタイムから除去した。Codex側のenvironment action実行機能自体と公開APIは削除していない。

### 2.4 操作bindingの分離

`src/m18-action-bindings.ts`へ物理操作から`DeckController`への配送を分離した。

- Agent、Joystick、Encoderはdown/upを維持
- `MIC`はpress/release対応のネイティブMicro経路を維持
- 公式キーはCodexのlive keycap registry経路を使用
- Usage表示はControllerへ登録
- Resetは既存の1.2秒長押し確認を使用
- scene離脱時に表示登録とキャッシュを解除

これにより`src/m18.ts`はUSBイベント、押下ownership、scene orchestrationへ責務を縮小した。

### 2.5 プロジェクト名優先表示

`MicroAgentSlot`へ任意の`projectLabel`を追加した。rendererのsidebar project groupと、構造化slot、task、thread、workspace、summaryから明示名称を探し、名称がない場合だけcwd／root pathのbasenameを使用する。

Agent表示は次の優先順にした。

1. プロジェクト／workspace名
2. タスク／セッション名
3. `New chat`、`Not assigned`、接続状態

プロジェクト名がある場合、64×64面ではプロジェクト名を主表示、タスク名を小さな補助行として描画する。状態色、選択、host badge、context ringは維持した。

### 2.6 relayの安全境界

remote Agentでも同じ表示を行うため、`projectLabel`をsnapshotの任意フィールドとして配送可能にした。

- 最大80文字
- basenameのみ
- `/`または`\`を含む値をrelay parserで拒否
- renderer snapshotは必要フィールドだけを明示的に構築
- native slotオブジェクト全体や絶対パスをrelayへ流さない
- mirror統合時は所有hostの安全なlabelを優先し、欠落時だけ他mirrorから補完

`docs/ARCHITECTURE.md`と`docs/MULTI_HOST.md`もこの境界へ更新した。

## 3. リファクタリング結果

| 変更前 | 変更後 |
|---|---|
| `m18.ts`の固定18 binding配列 | catalog→layout→binding factory→scene controller |
| 操作数とmanifest UUIDの関係が暗黙 | 45物理操作と53公開アクションを明示分離 |
| 下段キーがenvironment actionへ直結 | 3面の直接選択へ統一 |
| release時に現在bindingを参照 | key-down時のbinding ownershipを保持 |
| Agent表示は`slot.title`のみ | project primary＋task secondary＋fallback |
| renderer slotをspread | relay可能なfieldだけを明示抽出 |
| project label安全条件が未定義 | 正規化・検査を`project-label.ts`へ分離 |

大規模な`DeckController`／CDP transport／SVG rendererの全面分割は、今回の機能実装に必要な境界へ変更を限定し、公開APIを維持した。追加した各モジュールにより、今後の分割をM18入力やlabel仕様から独立して進められる状態にした。

## 6. 未検証境界

この環境にはRust `cargo`がなく、既存のadapter release binaryもなかったため、M18 adapterを含む最終配布ディレクトリは再生成できなかった。Rust adapterソースには変更を加えていない。M18 TypeScriptエントリはesbuildによる単独bundleを実行し、合格している。

実機確認では次を残す。

1. Rust stableとWindows C++ build toolsがある環境で`npm run build:m18`を実行する。
2. 下段3ボタンが常に対応する面へ直接移動することを確認する。
3. 全45操作を実機で押下する。
4. `MIC`とEncoderのdown/upを確認する。
5. Resetが短押しで不発、1.2秒長押しで1回だけ発火することを確認する。
6. local／remote Agentでプロジェクト名が表示され、絶対パスがログ・relay payloadへ出ないことを確認する。

上記のビルド／実機検証が終わるまでは、M18実機を含む完全合格とは扱わない。

## 7. ロールバック

- featureブランチから切り替えれば元ブランチの実装へ戻せる。
- manifest UUIDは変更していないため、既存VSD Craft profileは保持される。
- 直接接続版の旧下段environment action動作が必要な場合は、旧ブランチの`src/m18.ts`へ戻す。
- relayの`projectLabel`は任意追加フィールドなので、旧peerは無視できる。

## 8. 判定

コード、型検査、単体／統合テスト、通常配布、VSD Craft配布、release auditは合格した。45操作・3面切替・project名優先表示・relay basename制限は実装済みである。

Rust adapterを含むM18配布buildと実機smokeは環境不足により未完了であり、完了後に本報告書へ結果を追記する。
