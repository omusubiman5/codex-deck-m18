# Codex Deck M18 実装計画書 V1

## 1. 文書情報

- 版：V1
- 作成日：2026-08-19
- 対象：Windows／macOS、VSD Craft構成、M18直接接続構成
- 正本要件：`ニーズ.md`
- 実装境界：`修正方針.md`
- 実施・合格条件：`実行方針.md`

本書は、45個の必須操作をM18の15 LCDキー×3シーンへ収容し、同時に既存実装を安全にリファクタリングするための実装計画である。機能削減を伴う整理は行わない。

## 2. 到達目標

1. 必須操作45個を、重複・欠落なく15件×3シーンへ固定配置する。
2. 下段左・中央・右をシーン1・2・3への直接切替に統一する。
3. Agentキーはプロジェクト名を主表示とし、タスク／セッション名を補助情報として扱う。
4. 公式30キー、Joystick下方向、Reasoningエンコーダ押下、Usage Overview／Reset、New Task、ホスト切替をすべて配布・検証対象にする。
5. 現在の大きなController、CDPブリッジ、描画モジュールを責務別に分割し、変更時の影響範囲を限定する。
6. Stream Deck版、VSD Craft版、M18直接接続版、Windows／Mac relayを退行させない。

## 3. 数量と用語の固定

### 3.1 物理操作は45個

| 区分 | 個数 | 備考 |
|---|---:|---|
| Agent | 6 | Codex MicroのAgent 1～6 |
| Joystick | 4 | 上・下・左・右 |
| Reasoningエンコーダ押下 | 1 | down/upを保持 |
| ホスト切替＋health | 1 | Windows／Mac |
| Usage | 3 | Limit、Overview、Reset |
| 公式キー | 30 | New Task、MIND+、MIND-を内包 |
| 合計 | 45 | 15 LCDキー×3シーン |

下段3ボタンは面切替であり、45操作へ加算しない。

### 3.2 manifestアクション数とは分ける

現在のVSD Craft manifestには53アクションがある。これは6つの動的Microスロット、専用アクション、公式キー用アクションなどを含むプラグインAPI上の公開数であり、M18へ重複なく配置する45操作とは別の数量である。

V1では互換性維持のためmanifestの既存UUIDを削除しない。物理45操作から既存UUIDへの対応表を一元管理し、同じ能力を表す重複UUIDを盤面へ二重配置しない。

## 5. Agent表示仕様

### 5.1 表示優先順位

1. プロジェクト名
2. タスク／セッション名
3. `New chat`、`Not assigned`、接続状態などのフォールバック

64×64表示ではプロジェクト名を最大2行の主表示とする。タスク名を同時表示できる場合だけ小さな補助行に置き、判読性が落ちる場合はプロジェクト名を優先する。選択状態、Agent状態色、host badge、context ringは維持する。

### 5.2 プロジェクト名の取得

- Codex rendererの構造化されたtask／workspace状態を第一候補にする。
- 取得できない場合はworkspace rootまたはcwdのbasenameだけを使用する。
- フルパス、prompt、response、rollout本文から名称を推測しない。
- 取得不能時は現在の`slot.title`へフォールバックする。

### 5.3 relayとプライバシー

remote Agentにもプロジェクト名を表示するため、`projectLabel`をrelay snapshotへ追加する。送信可能なのは明示的名称またはbasenameだけとし、絶対パスは送信しない。プロトコル変更時に`docs/ARCHITECTURE.md`と`docs/MULTI_HOST.md`のプライバシー記述も更新する。

## 6. リファクタリング方針

### 6.1 原則

- 挙動を固定するcharacterization testを先に追加する。
- 機能追加とファイル分割を同一コミットで混在させない。
- 公開UUID、relay互換、保存済みVSD Craft配置を壊さない。
- 1つの定義から物理配置、manifest検証、テスト期待値を生成する。
- privateなCodex renderer探索が失敗した場合は、黙って誤動作せずhealthとログへ理由を出す。

### 6.2 追加する中核モジュール

| 新規モジュール | 責務 |
|---|---|
| `src/action-catalog.ts` | 45操作のID、表示名、実行種別、既存UUID対応 |
| `src/m18-layout.ts` | 3シーン×15配置、完全性検査、下段切替定義 |
| `src/project-label.ts` | projectLabelの正規化、basename化、フォールバック |
| `src/controller/command-router.ts` | local／remote配送、押下先の固定 |
| `src/controller/agent-state.ts` | 6 Agentの統合、選択、host ownership、health |
| `src/controller/display-coordinator.ts` | 登録面の差分描画とanimation scheduling |
| `src/bridge/cdp-client.ts` | CDP接続、再接続、evaluate、応答管理 |
| `src/bridge/snapshot-reader.ts` | rendererからのsnapshot取得と正規化 |
| `src/bridge/command-dispatcher.ts` | Agent、Joystick、Encoder、keycap、Reset配送 |
| `src/render/agent.ts` | Agent／project label描画 |
| `src/render/usage.ts` | Usage 3種の描画 |
| `src/render/keycap.ts` | 公式／builtin keycap描画 |

ファイル名は実装時に既存importとの整合で微調整できるが、責務の境界は維持する。

### 6.3 `DeckController`の縮小

現在の`DeckController`は接続、snapshot更新、Agent routing、remote配送、登録管理、描画、animation、Usage reset holdを保持している。V1では外部APIをfacadeとして残し、内部処理を次へ委譲する。

- `AgentStateService`：snapshotとrelayから表示対象6件を決定
- `CommandRouter`：押下時に確定したhostへlocal／remote配送
- `DisplayCoordinator`：登録アクションの描画、signature cache、animation
- `UsageController`：usage選択、Reset hold状態

移行完了後も`actions.ts`から見える`DeckController`公開メソッド名は原則維持する。

### 6.4 CDPブリッジの分割

`codex-micro-renderer-bridge.ts`はCDP transport、renderer内部探索、snapshot抽出、コマンド解決、DOM fallbackを分離する。rendererへ注入する処理はテンプレート文字列の断片ではなく、入力・出力型を持つexpression builderとして管理する。

分割後も次を維持する。

- loopback CDPのみ
- stable thread identityによるAgent選択
- 公式keycap handlerの利用
- Reset credit消費の確認
- Codex更新時の明示的なhandler不在エラー

### 6.5 描画の分割

`render.ts`のpublic関数シグネチャを一旦re-exportで維持し、Agent、Usage、host、keycapを別ファイルへ移す。共通palette、XML escape、font fittingだけを`render/shared.ts`へ置く。

Agent描画の入力は引数列ではなく次の値オブジェクトへ移行する。

```ts
type AgentRenderModel = {
  projectLabel: string;
  taskLabel?: string;
  status: AgentVisualStatus;
  selected: boolean;
  theme: ThemeMode;
  hostBadge?: string;
  hostHealth: HostHealthState;
  contextUsedPercent?: number;
};
```

### 6.6 action定義の一元化

`OFFICIAL_KEYCAP_IDS`、`ADDITIONAL_KEYCAPS`、`actions.ts`、`static/manifest.json`、VSD Craft検証に散在する対応を`action-catalog.ts`から検査できる形にする。

特に`MIC`はhold可能な既存Dictationアクション、`NEW`はNew Task、`MIND+`／`MIND-`はReasoning調整へ対応させる。公式30件の各IDが物理配置と実行経路をちょうど1件持つことをテストする。

### 6.7 M18面管理

`m18.ts`の固定18件配列を廃止し、`M18SceneController`へ次を持たせる。

- current scene：0～2
- LCD 0～14のbinding登録解除と再登録
- 下段15～17の直接scene selection
- scene変更時の15面一括再描画
- 押下中にscene変更した場合のrelease配送保証
- 再起動時の既定scene 1

VSD Craft構成では同じ`m18-layout.ts`をprofile生成・検証の入力に使い、直接接続構成との配置差を作らない。

## 7. 実装フェーズ

### Phase 0：基準固定

- 現行テスト、型検査、通常build、VSD Craft validationを実行する。
- 53 manifest UUID、公式30 ID、relay protocol fixtureを保存する。
- 現行Agent、Usage、host、keycap SVGのcharacterization testを追加する。

完了条件：変更前挙動を再現可能なテスト基準がある。

### Phase 1：45操作カタログと3面定義

- `action-catalog.ts`と`m18-layout.ts`を追加する。
- 45件、3×15、重複なし、公式30件完全一致をテストする。
- 既存manifest 53 UUIDとの対応漏れを検査する。
- この段階ではruntime挙動を変えない。

完了条件：数量と配置がコード上の唯一の定義源になる。

### Phase 2：プロジェクト名表示

- `MicroAgentSlot`と`RoutedAgentSlot`へ`projectLabel?: string`を追加する。
- renderer snapshotから構造化project情報を取得する。
- relay protocolへbasename限定のprojectLabelを追加する。
- Agent rendererを主表示project、補助表示taskへ変更する。
- project取得不能時の既存title fallbackを確認する。

完了条件：local／remote Agentの双方でプロジェクト名が優先表示され、フルパスを送信しない。

### Phase 3：Controller分割

- Command routing、Agent state、Usage、displayを順に抽出する。
- 各抽出の前後で既存公開APIとテストを維持する。
- 1回の変更で1責務だけを移す。

完了条件：`DeckController`がfacade／orchestration中心になり、描画・routing・Usageの判断を直接持たない。

### Phase 4：CDPブリッジ分割

- CDP transportを抽出する。
- snapshot readerとproject metadata抽出を分離する。
- command dispatcherとhandler discoveryを分離する。
- Codex version差分をadapter層へ閉じ込める。

完了条件：snapshot取得と各コマンドを個別にfixture testできる。

### Phase 5：描画分割

- Agent、Usage、host、keycap rendererを分割する。
- 既存exportはbarrelから維持する。
- project＋task表示の64×64 visual fixtureを追加する。

完了条件：既存画像の意図しない差分がなく、新表示の文字切れがない。

### Phase 6：M18 3シーン実装

- 直接接続版へ`M18SceneController`を導入する。
- 下段3ボタンをscene 1～3の直接切替へ変更する。
- 45操作をcatalogからbindingへ変換する。
- VSD Craft用3シーンprofileの生成／検証をcatalog駆動へ変更する。

完了条件：15×3の全操作を実機から実行でき、下段ボタンが常に同じ面へ移動する。

### Phase 7：統合、配布、文書整理

- Windows／macOS、local／relay、VSD Craft／直接接続を統合検証する。
- README、M18、MACOS、WINDOWS、MULTI_HOST、ARCHITECTUREを実装結果へ同期する。
- 旧2面＋メーカー標準面、下段environment action固定などの矛盾記述を除去する。
- installerとrelease auditを実行する。

完了条件：配布物と正本文書が同じ45操作・3面仕様を示す。

## 9. 互換性と移行

- manifest UUIDはV1で削除・変更しない。
- relay protocolは旧peerが`projectLabel`を無視できる追加フィールドとして導入する。
- 保存済みVSD Craft profileは破壊せず、新しい3面profileを別名で生成して切替可能にする。
- 直接接続版の旧environment action下段配置は設定バックアップへ退避し、自動的に上書きする場合は復元手順を用意する。
- `render.ts`と`DeckController`の既存importは移行期間中re-export／facadeで維持する。

## 10. リスクと対策

| リスク | 対策 |
|---|---|
| Codex更新でproject fieldが変わる | adapter＋fallback、healthログ、fixtureを版別管理 |
| リファクタリングと機能追加の同時退行 | Phaseを分離し、各Phaseで全テストを通す |
| 53 manifest actionと45物理操作の混同 | catalogに`capabilityId`と`manifestUuid`を別フィールドで保持 |
| remoteへフルパスが漏れる | basename正規化後だけprotocolへ渡し、拒否テストを追加 |
| scene切替時にreleaseが消える | key-down時のbindingをpress ownershipとして保持 |
| 64×64でproject名が読めない | 2行fit、task補助行の省略、visual fixtureで確認 |
| 既存VSD配置が壊れる | UUID不変、新profileを並行生成、rollback手順を維持 |

## 11. 完了判定

次をすべて満たした場合だけV1実装完了とする。

- 45操作が15件×3面へ重複なく収まる。
- 下段3ボタンから3面へ直接切り替わる。
- 公式30キー、Joystick 4方向、Encoder、Host、Usage 3種が動作する。
- Agentキーはproject名を優先し、取得不能時だけtask名へfallbackする。
- remote snapshotに絶対パスを含めない。
- manifest 53 UUIDと既存profile互換を維持する。
- TypeScript、全テスト、通常build、VSD Craft validation、M18 build、release auditが合格する。
- Windows／macOSの実機smoke結果を記録する。
- 正本文書とREADMEが実装結果と一致する。

## 12. V1対象外

- 45操作を超える第4シーン
- 任意レイアウトを編集する独自UI
- Codex Desktop、VSD Craft、M18 firmwareの改変
- prompt／response内容からのプロジェクト推測
- 既存manifest UUIDの整理・削除

これらはV1完了条件を満たした後に別版で判断する。V1の必須45操作を対象外へ移すためにこの節を使用してはならない。
