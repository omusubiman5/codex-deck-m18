# Codex Deck M18 テスト結果 V1

## 1. 総合判定

**総合判定：live不合格・再試験待ち。オフライン安全修正は合格。**

以前記載した「Windows実機smoke合格」「plugin 1 process確認」「LIVE-01／02／06合格」は撤回する。その後にCodexの多重起動とクラッシュが発生しており、単純起動を最初に確認していなかったため、live合格の根拠として無効である。

2026-08-19の今回作業ではアプリを起動・停止せず、監視回路の修正とオフライン試験だけを実施した。

## 2. 原因として確認した実装

- VSD Craft plugin起動時、`windows-bridge-supervisor.ts`がwatcherへ`-RecoverExistingSession`を常に渡していた。
- watcherの`RecoverExistingSession`は消費されず、監視中ずっと回復許可として働いていた。
- watcher生存中の回復回数上限がなかった。
- watcher再起動をまたぐ永続的なcooldown／circuit breakerがなかった。
- Codex main processが複数でも強制再起動を拒否する条件がなかった。
- 回復試行後に`hadHealthyBridge = true`としており、実際にhealthyへ戻った確認なしで次の回復根拠を作っていた。

これらにより、plugin再起動、watcher再生成、bridge degraded、Codex process交代が重なると、稼働中Codexへ複数回の強制再起動を要求できる状態だった。

## 3. 安全修正

- plugin supervisorから`-RecoverExistingSession`を除去し、観測専用にした。
- Codex main processが厳密に1個でない場合は自動回復を禁止した。
- watcher生存中の自動回復を最大1回に制限した。
- `%LOCALAPPDATA%\CodexDeck\watcher-recovery.json`へ回復試行を保存し、30分の永続回路遮断を追加した。
- 回復試行記録を`-ForceRestart`より前に保存するようにした。
- 起動時の回復権限は最初のrunning generation判定で消費するようにした。
- 回復を試しただけでhealthy扱いにする処理を削除した。

初回オフライン試験では2件失敗した。

1. PowerShellの日時差分でnullable型の扱いが誤っていた。
2. 既存テストが旧仕様の`RecoverExistingSession`付与を要求していた。

両方を修正後、同じ試験一式を再実行し全件合格した。この過程でCodex Desktop、VSD Craft、M18の起動・停止・process操作は行っていない。
