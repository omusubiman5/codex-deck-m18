# README 正確性・可読性の原因調査

## 1. 事象

READMEの記述に、実装と一致しない箇所と、読者が推奨手順を追えなくなる構成上の欠陥がある。

- 記載どおりに導入手順を実行すると、Windowsでは途中で失敗する。
- 記載されたログ出力先に、実際にはファイルが生成されない場合がある。
- 同一項目について、README内の3か所が異なる内容を主張している。
- 「旧方式」見出しの配下に、共通説明とライセンス表記を含むREADMEの残り全体が入っている。

調査日時: 2026-08-16（JST）

## 2. 確認した対象

| 項目 | 値 |
|---|---|
| README | 277行、`76cf327` 時点 |
| package.json | `codex-stream-deck` 0.7.0-hotfix.2 |
| 推奨構成 | VSD Craft転用 |
| 旧方式 | mirajazz直接接続（ソース保持） |

照合対象の実装:

- `src/m18.ts`、`src/codex-deck-paths.ts`、`m18-adapter/src/main.rs`
- `scripts/Install-VSDCraft-CodexDeck.ps1`、`scripts/install-vsd-craft-codex-deck-macos.sh`
- `scripts/Watch-CodexDeck-M18.ps1`、`scripts/Start-CodexDeck-M18.ps1`
- `package.json` scripts、`docs/` 配下

## 3. 個別の不整合

### 3.1 ログ出力先の誤記（README L230）

READMEは3種のログをすべて `%LOCALAPPDATA%\CodexDeck\` 配下と記載している。

```text
| %LOCALAPPDATA%\CodexDeck\m18.log | watcher、Codex接続、M18接続、描画同期 |
```

`m18-events.log` と `codex-micro-bridge.json` は `codexDeckStateRoot()` を経由するため記載どおりである。

```ts
// src/codex-deck-paths.ts:10
return win32.join(localAppData ?? win32.join(home, "AppData", "Local"), "CodexDeck");
```

しかし `m18.log` だけは経路が異なり、watcherスクリプト自身の配置場所の親フォルダへ書き込む。

```powershell
# scripts/Watch-CodexDeck-M18.ps1:5
$log = Join-Path (Split-Path -Parent $runtimeRoot) 'm18.log'
```

READMEが常駐運用の例として示す配置は `C:\path\to\CodexDeck\M18\Watch-CodexDeck-M18.ps1`（L221）であり、この場合の実際の出力先は `C:\path\to\CodexDeck\m18.log` となる。`%LOCALAPPDATA%` 配下になるのは、利用者が偶然そこへ配置した場合だけである。

READMEはL234で「入力が反応しない場合は最初に `m18-events.log` を確認」と案内しているため、利用者は誤った場所を探しに行くことになる。

### 3.2 Windows導入の必須前提が未記載（README L45-51）

READMEはWindows導入を次の1コマンドとして提示している。

```powershell
.\scripts\Install-VSDCraft-CodexDeck.ps1 -VSDCraftInstallerPath '...' -Launch
```

実際のスクリプトには、READMEに書かれていない3つの停止条件がある。

**(a) ESETコマンドラインスキャナ必須**

```powershell
# scripts/Install-VSDCraft-CodexDeck.ps1:105-107
$scanner = 'C:\Program Files\ESET\ESET Security\ecls.exe'
if (-not (Test-Path -LiteralPath $scanner -PathType Leaf)) { throw 'ESET command-line scanner was not found.' }
```

ESET非導入環境では確実に例外終了する。回避用の `-SkipEsetScan` スイッチが存在するが、READMEに記載がない。

**(b) `dist-vsd-craft` の事前ビルド必須**

```powershell
# scripts/Install-VSDCraft-CodexDeck.ps1:94-95
$pluginSource = [IO.Path]::GetFullPath((Join-Path $root 'dist-vsd-craft\com.simeo.codex-deck.sdPlugin'))
$manifestPath = Assert-File (Join-Path $pluginSource 'manifest.json') 'VSD Craft plugin manifest'
```

Windows版インストーラはビルドを行わない。READMEはL39で `npm run validate:vsd-craft` を「ビルドと検証」という任意にも読める見出しで置いているが、実際はインストーラの必須前段である。さらに `npm ci` はREADME L181の「ビルド」節にしかなく、その節はL64の「旧方式」見出しの配下にある。

**(c) インストーラの署名検証必須**

```powershell
# scripts/Install-VSDCraft-CodexDeck.ps1:101-102
$signature = Get-AuthenticodeSignature -LiteralPath $installer
if ($signature.Status -ne 'Valid') { throw "..." }
```

**macOSとの非対称性**

macOS版スクリプトは自分でビルドを実行するため、事前ビルドを必要としない。

```zsh
# scripts/install-vsd-craft-codex-deck-macos.sh:52-55
"$node_candidate" scripts/build.mjs
"$node_candidate" scripts/build-launcher.mjs
"$node_candidate" scripts/build-vsd-craft.mjs
"$node_candidate" scripts/validate-vsd-craft.mjs
```

READMEは両OSの手順を同じ粒度で並置しているため、この前提差が読み取れない。

### 3.3 「必要環境」が推奨構成と矛盾（README L167-174）

現行の必要環境は次を挙げている。

- Windows 10以降
- Rust stable
- Windows向けRustをビルドできるC++ツールチェーン

問題は2点。

1. READMEはL3とL53でmacOS対応を宣言しているが、OS要件はWindowsのみを挙げている。
2. 推奨構成にRustとC++ツールチェーンは不要である。`build:vsd-craft` はcargoを呼ばない。

```json
"build:vsd-craft": "npm run build && node scripts/build-vsd-craft.mjs",
"build:m18": "cargo build --release --manifest-path m18-adapter/Cargo.toml && node scripts/build-m18.mjs",
```

cargoを使うのは旧方式の `build:m18` だけである。現行READMEでは必要環境が旧方式節の中にあるため、推奨構成の読者が不要なツールチェーン導入を強いられる。

### 3.4 下段3ボタンの記述が3か所で矛盾

同一の物理ボタンについて、README内の3か所が異なる内容を主張している。

| 箇所 | 記述 |
|---|---|
| L35（VSD Craft節） | シーンシフトだけを設定し、Codex操作は割り当てない |
| L98（機能対応表） | Codex環境アクション1～3 → 下段3ボタン |
| L112、L147-149（特徴・キー割当表） | `environmentAction1`～`environmentAction3` を実行 |

実装上、`environmentAction` を下段3ボタンへ割り当てているのは**旧方式のランタイムだけ**である。

```ts
// src/m18.ts:61-67
bindings = [
  agent(0), ..., agent(5),
  micro("ACT06"), ..., micro("ACT12"),
  joystick("up", ...), joystick("left", ...), joystick("right", ...),
  environmentAction(1), environmentAction(2), environmentAction(3)
];
```

VSD Craft運用時はこのランタイムが起動しない（README L5、およびインストーラの `Stop-LegacyM18Runtime` / `Disable-LegacyM18Startup` による明示的な無効化）。したがってL98・L112・L147-149は旧方式限定の記述だが、そのスコープが示されていない。

なおLCD 1–15の割当は両方式で一致するため、矛盾しているのは下段3ボタンのみである。VSD Craft側の設定キー（Agent 1～6、FAST、APPR、REJ、SPLIT、MIC、CODEX、上・左・右）は、旧方式の `agent(0..5)` / `ACT06`〜`ACT12` / `joystick(up|left|right)` と1対1で対応する。

### 3.5 会議パネル手順の説明ずれ（README L37）

READMEは「各シーンへ15個のWindowsショートカットと専用アイコンを設定する手順」と記述しており、全体が手作業に読める。実際には手作業は空シーン4つの作成のみで、残りは自動化されている。

```text
npm run configure:meeting-panels
```

`package.json` に `configure:meeting-panels` が定義済みで、`docs/vsd-craft/MEETING_PANELS.md` が正しい手順を持つ。またこの機能はWindowsショートカットに依存するWindows専用機能だが、READMEにその限定がない。5列×3行=15という数値自体は正確である。

### 3.6 参照されていないドキュメント

READMEからたどれない実用ドキュメントがある。

- `docs/TROUBLESHOOTING.md` — 起動・ブリッジ不成立時の対処。ログ節から張るべき内容
- `docs/WINDOWS.md` — Windows単独構成
- `docs/ARCHITECTURE.md`
- `docs/vsd-craft/原因調査.md`、`docs/vsd-craft/対応報告.md`

一方でリンク切れは存在しない。README記載の全リンク先ファイルは実在する。

### 3.7 その他の可読性低下要因

- **日本語文中の英文**: L261「A Mac with Xcode is required to build and install it, even when the phone will control only Windows.」、L265「independent implementation」。日本語文中で唐突に読みにくいが、**翻訳漏れではない**。3.8を参照。
- **価格の記載位置**: L12-15の購入情報が冒頭付近にある。「2026年8月16日時点」の価格・クーポンは陳腐化が確定している情報であり、導入判断の主動線に置く必然性がない。
- **空の見出し**: L64「## 旧方式：M18直接接続」の本文は2行のみで、直後にL68「## Codex Deckとは」が来る。見出しが内容を持たない。
- **同名ドキュメント3系統**: 「ニーズ／修正方針／実行方針」が `docs/vsd-craft/`、`docs/codex-micro-m18/`、リポジトリルートの3か所に存在し、どれが現行かの注記がない。
- **バージョン情報の欠如**: 「Codexの更新後に追従修正が必要になる可能性」を警告しながら、動作確認済みのCodex Desktopバージョンが書かれていない。`docs/vsd-craft/原因調査.md` には 26.810.7004.0 の記録がある。

### 3.8 英文の帰属表記はテストで固定されている（当初の誤判定）

3.7で「翻訳漏れ」と分類した2つの英文は、当初の調査では単純な訳し忘れと判断した。これは**誤り**である。修正作業中に`npm test`が2件失敗して判明した。

```ts
// test/release-docs.test.ts:13-18
for (const document of [readme, install, release]) {
  const prose = document.replace(/^> ?/gm, "");
  assert.match(prose, /Mac(?: with)?[^.\n]*Xcode/i);
  assert.match(prose, /control only\s+(?:a\s+)?Windows/i);
  assert.match(prose, /App Store/);
}

// test/release-docs.test.ts:26-30
for (const document of [readme, release]) {
  assert.match(document, /Shikhar \(@xikhar\)/);
  assert.match(document, /https:\/\/x\.com\/xikhar/);
  assert.match(document, /independent implementation/i);
}
```

この2つの英文は、iPhone companionの配布境界（Mac+Xcode必須、ストア配布なし）と、上流モバイル実装の独立性に関する帰属表記であり、`README.md`・`docs/IOS_INSTALL.md`・`docs/RELEASE_0.7.0.md`の3文書で同一文言を保つようテストで固定されている。日本語へ置き換えると3文書間の一致が崩れ、テストが失敗する。

したがって、この英文は**意図的に維持されるべき**である。可読性の問題は残るため、原文を保持したうえで日本語の補足を併記する方法で対処する。

**教訓**: README文言はテストの検証対象である。文面変更後は`npm test`を必ず実行する。

## 4. 根本原因

### 主原因: 追記型更新による構成崩壊

READMEのコミット履歴は次の順である。

```text
0661b0c Write M18 project README          ← 旧方式前提で全体を執筆
7d2f206 Document inherited Codex Deck features
ed88d1c Map M18 bottom keys to native environment actions
1b43130 feat: add VSD Craft M18 integration   ← VSD Craft節を冒頭へ挿入
adaa7f9 feat: add macOS VSD Craft support
7e14b61 docs: add M18 purchase information
76cf327 feat: add branded VSD Craft meeting panels
```

READMEは当初、旧方式（M18直接接続）だけを前提として全体が書かれていた。方式転換にあたり、VSD Craft節を**冒頭に挿入**し、既存本文の先頭に「## 旧方式：M18直接接続」という見出しを1つ足す方法で対応した。

この操作により、見出しの効力範囲が意図を超えた。Markdownの `##` は次の同レベル見出しまでではなく、文書構造上そこから下位を包含するため、L64以降の全セクション（`Codex Deckとは`、`キー割当`、`必要環境`、`ビルド`、`ログ`、`設計資料`、`上流から継承している機能`、`謝辞`、`OSSとライセンス`）が「ロールバック用の旧方式」の説明として読める状態になった。

L66の一文がこれを明示的に補強している。

```text
以下はロールバック用のmirajazz直接接続方式です。VSD Craft運用時には起動しません。
```

結果として、
- 両方式に共通の説明（3.4のキー割当、機能一覧）が旧方式限定に見える
- リポジトリ全体に関わるライセンス表記・謝辞が旧方式限定に見える
- 推奨構成の節は実質40行しかなく、必要環境・ビルド前提・ログ確認手順を持たない

推奨構成の読者は、必要な情報を「旧方式」節から拾い読みせざるを得ず、その際に旧方式限定の記述（3.4の下段3ボタン、3.3のRust要件）を推奨構成の要件と誤認する。

### 副次要因1: 手順の検証が実装追従していない

3.2のESET依存と事前ビルド依存は、いずれもスクリプト側に後から追加された防御的処理である。README側の手順記述は追従していない。スクリプトの `param()` ブロックに定義済みのスイッチ（`-SkipEsetScan`、`-SkipVSDCraftInstall`）が一度もREADMEに現れていないことが、追従漏れを示している。

### 副次要因2: README文言のテスト固定範囲が文書化されていない

3.8のとおり、READMEの一部文言は`test/release-docs.test.ts`で3文書横断の一致を強制されている。しかしREADME自身にもCONTRIBUTING.mdにもその旨の記載がないため、READMEを編集する者は該当箇所が保護対象であることを知り得ない。本調査でも一度この英文を翻訳して破壊し、テスト実行で初めて検出した。

### 副次要因3: 実装の出力先が2系統ある

3.1のログ問題は、状態ファイルの出力先解決が2経路存在することに起因する。TypeScript側は `codexDeckStateRoot()` で一元化されているが、PowerShell watcherは自身の配置場所からの相対解決を行う。READMEはこの差を認識せず、3ファイルを同一表に並べた。

| 対象 | 影響 |

| Windows新規導入者 | 3.2により手順が失敗する。ESET非導入環境では回避策も分からない |
| macOS新規導入者 | 3.3によりOS要件から対象外に見える |

## 7. 結論

事実誤りは3.1（ログパス）と3.2（未記載の必須前提）の2件で、いずれも手順を実行不能または誤誘導にする実害を持つ。残りの不整合3.3・3.4・3.5は、記述自体は旧方式の説明として正しく、**スコープが示されていない**ことに起因する。

したがって根本対処は文言の個別修正ではなく、方式ごとに導入経路を分離し、共通説明を両方式の上位へ引き上げる構成の再編である。3.1と3.2は構成再編とは独立に、事実修正として同時に行う。

3.8で判明したとおり、README文言の一部はテストによる保護対象である。再編時は原文を維持したうえで補足する方針とし、作業後に`npm test`で検証する。この保護範囲の存在自体もREADMEから読み取れないため、あわせて明文化する。
